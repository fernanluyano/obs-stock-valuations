# Development notes

Technical reference for working on this plugin. See `README.md` for user-facing documentation (what ships in the in-app Help screen's spirit — keep that file free of file/function names and build details; put those here instead).

## Project layout

| File | Responsibility |
|---|---|
| `main.ts` | Plugin entry point — registers the view, ribbon icon, command, and settings tab; constructs `DataRepository` and awaits its `load()` |
| `dataRepository.ts` | Owns every read/write of persisted state (settings + the valuation table, stored as vault notes; `data.json` is only a device-local cache) — see **Data persistence (implementation)** below |
| `view.ts` | The calculator + table UI (`ItemView`), including form rendering, chart rendering, screen state, and the research-link menus/modals |
| `calculations.ts` | Pure valuation math (WACC, cost of equity, DCF, Graham, Ten Cap, DDM, Payback Time, PEG ratio, margin of safety, owner earnings yield) |
| `settings.ts` | Settings schema, defaults, and the settings tab UI (imperative `display()` for pre-1.13 Obsidian, plus the declarative `getSettingDefinitions()` for 1.13+) |
| `valuationStore.ts` | Types for saved valuations and the in-memory/persisted table, including a ticker's `HistoryEntry[]` timeline |
| `historyStore.ts` | Pure logic for a saved valuation's history timeline — building an entry (`buildHistoryEntry`), append-with-dedupe-by-day, single-entry delete, and 6-month/monthly compaction |
| `migrations.ts` | On-disk schema version + the v1→v2 (single-scenario → Bull/Base/Bear) migration, run once by `DataRepository.load()` |
| `noteSync.ts` | `ensureFolderExists`, shared by the vault adapter and research-note creation |
| `notes/` | Pure note text ↔ model: frontmatter reader/patcher, `kinds` (tags, `state`), `paths`, `valuationNote` (`TICKER.md`), `settingsNote` (`Settings.md`) |
| `table/` | Own Markdown table parser/serializer (ported from `../obs-nestegg`) |
| `storage/` | `VaultPort` (what the repository needs from the vault) and `ObsidianVault`, the only file that touches the vault API |
| `priceProvider.ts` | Yahoo Finance quote lookup |
| `units.ts` | Scale (ones/thousands/millions/billions) types, labels, and multipliers |
| `format.ts` | Number sanitization/formatting for form inputs and display |
| `helpText.ts` | Per-field help tooltip copy |
| `docs.ts` | Content for the in-app help/methodology screen — formulas, sources, per-method fit guidance |

### Valuation methods (implementation)

- **WACC** (`calculations.ts: calcWacc`) — cost of equity via CAPM (`calcCostOfEquity`: `rfr + beta * mrp`), cost of debt as `intExp / totDebt` tax-adjusted by `taxRate`, blended by market-value weight (`mktCap` vs `totDebt`).
- **DCF** (`calcDcf`) — 10-year, two-stage free cash flow projection: `growth1to5` for years 1–5, `growth6to10` for years 6–10, discounted at WACC. Year 10 flows into a Gordon Growth terminal value at `terminalGrowth`, and `netDebt` is subtracted from enterprise value before dividing by `shares` to get equity value per share.
- **Reverse DCF** (`calcImpliedGrowth`) — fixes price and every other `DcfInputs` field, bisects for the `growth1to5` that makes `calcDcf(...)` equal price (`calcDcf` is monotonic increasing in `growth1to5` for a fixed `wacc`, so bisection is safe). Returns `NaN` when price falls outside what the `[lo, hi]` bracket (default `[-0.5, 1.0]`) can produce, which the UI shows as "—". `valuationCalc.ts: computeResultsForState` wires it into `Results.impliedGrowth`; `view.ts: renderResults()` surfaces it as its own labeled row in the results panel's "Other metrics" table (`HELP_TEXT.impliedGrowth` behind the row's `?` icon) rather than a grid — kept out of the "Margin of safety" table above it since it has no MoS of its own (see `mosRow`/`metricRow` in `renderResults()`).
- **Graham Formula** (`calcGraham`) — `EPS * (8.5 + 2g) * 4.4 / Y`, where `g` is expected EPS growth and `Y` is the current AAA bond yield.
- **Ten Cap** (`calcTenCap`) — owner earnings (`ocf - capex * mainPct`) valued at a 10x multiple, plus owner-earnings yield at the current price (`ownerEarningsYield`).
- **DDM** (`calcDdm`) — Gordon Growth, `dps * (1 + ddmGrowth) / (ke - ddmGrowth)`, discounted at cost of equity (`calcCostOfEquity`, surfaced as `Results.costOfEquity`), not WACC. Dividend payers only: returns `NaN` (shown as "—") for `dps <= 0` and for `ddmGrowth >= ke`. `dps` is per-share and never scaled (like `price`/`eps`); `ddmGrowth` is scenario-specific, like `grahamGrowth`. `dps` is auto-fillable via `fundamentalsProvider.ts` (TTM of `CommonStockDividendsPerShareDeclared`, falling back to `...CashPaid`). Shown everywhere DCF/Graham are: the Margin of safety table, both MoS charts (via `METHODS`), the saved-valuations table (Bear/Base/Bull columns), and history (in-app and in each ticker's note) (`HistoryEntry.ddm{Bear,Base,Bull}Iv`, plus a DDM line in the history chart). Sensitivity grid: `calcDdmGrid` (ke × growth, `null` where `calcDdm` is `NaN`), rendered by `view.ts: renderDdmSensitivityGrid()`. The `HistoryEntry` fields are optional, and `buildHistoryRow`/`buildHistoryNoteContent` read missing (or `null`) `ddm*` values as `NaN` via `historyIv()`, so entries from before the DDM render as "—". Saved records need no such handling — their results are rebuilt on load (see **Data persistence**).
- **Payback Time** (`calcPaybackTime`) — years of growing FCF (the DCF's own `growth1to5` / `growth6to10` / `terminalGrowth` stages, undiscounted) until the running sum reaches EV (`mktCap + netDebt`), final year interpolated. `NaN` for `fcf <= 0`, `0` when EV <= 0, `Infinity` past `PAYBACK_MAX_YEARS` (30). `paybackTone` maps it to the results row's dot color (≤ `PAYBACK_GOOD_YEARS` 8 green, ≤ `PAYBACK_OK_YEARS` 10 yellow, else red). A metric, not a valuation — "Other metrics" table, no MoS.
- **PEG ratio** (`calcPeg`) — `(price / eps) / (growth × 100)`, where `growth` is the Graham growth input (`grahamGrowth`, a fraction like every percent field once it's through `numFromState`), so it's scenario-specific. `NaN` (shown as "—") unless price, EPS and growth are all positive. `pegTone` colors it (≤ `PEG_GOOD` 1 green, ≤ `PEG_OK` 2 yellow, else red), reusing `PaybackTone`. Stored as `Results.pegRatio`, rebuilt on load like every other result (never in the note or the history). A metric, not a valuation — "Other metrics" table, no MoS, `HELP_TEXT.pegRatio` behind the `?`.
- Margin of safety: `marginOfSafety`.
- Sensitivity grid visibility: each `render*SensitivityGrid()` in `view.ts` first calls `showSensitivityGridIfValued()`, which shows that grid's block only when `hasIntrinsicValue()` (any of Bull/Base/Bear's IV is finite and non-zero — 0 is what a blank form computes); `updateSensitivityVisibility()` then hides the whole section if no grid was built. Relies on `recalculate()` recomputing all three scenarios' results on every keystroke, not just the active tab's.

These functions are pure and have no Obsidian dependency — see `tests/calculations.test.ts` for their exact behavior, including edge cases (zero shares, zero debt, non-positive bond yield, out-of-bracket reverse DCF, non-payer DDM, g ≥ ke, etc).

### Research links (implementation)

- Data: `SavedValuation.researchNotePath` (`valuationStore.ts`) — an optional vault path, set/cleared only from the table (never the calculator form). `view.ts: saveValuation()` explicitly carries it forward from `this.originalTicker`'s prior record (`plugin.data.getValuation(...)`) on every save, since the record object is otherwise rebuilt from scratch — don't lose this when touching that method.
- Gate: `settings.ts: researchLinksActive(settings)` — `true` only when `enableResearchLinks` is on **and** `researchNotesFolder` is non-blank (no shipped default folder). The table (`view.ts`) is the only place the Research column shows — history notes don't carry research links.
- Table UI: `view.ts: renderResearchCell()` renders either an open+unlink icon pair (linked, file resolves), a "Link note" pill with a "not found — click to relink" tooltip (path stored but `Vault.getAbstractFileByPath` can't resolve it), or the same pill with a neutral tooltip (never linked). Both the open and unlink icon clicks (and the row-delete flow) go through `ConfirmModal` for anything that removes state — `ConfirmModal` takes an optional `confirmLabel`/`confirmCls` now (`"mod-warning"` default for destructive actions, `"mod-cta"` used for the create confirmation below) since it's shared across all of these.
- `openLinkNoteMenu()` shows an Obsidian `Menu` with two items: "Choose an existing note…" opens `LinkNoteSuggestModal` (a `FuzzySuggestModal<TFile>` over `vault.getFiles()` — intentionally not markdown-only, since the plugin never reads the file), and "Create a new note here…" builds the path as `<folder>/<TICKER>-research.md` directly — **no filename prompt**; the ticker convention is fixed, unlike the free-form naming "Choose existing" allows for a note you already have. It checks `Vault.getAbstractFileByPath()` first: if something's already there it shows an error `Notice` and stops (no confirm, no overwrite); otherwise it shows a `ConfirmModal` naming the exact path before calling `createAndLinkResearchNote()`, which re-checks existence itself as a race-condition guard and errors the same way if it lost the race. Both paths funnel into `setResearchLink()`, which mutates the in-memory record (from `plugin.data.getValuation()`) and calls `plugin.data.persistValuations()`.
- Note creation reuses `noteSync.ts`'s exported `ensureFolderExists()` rather than duplicating parent-folder creation logic.
- "Research notes folder" is a plain text field, no autocomplete (a hand-rolled `AbstractInputSuggest` subclass was tried and dropped — couldn't confirm it was actually firing at runtime, not worth the unverifiable custom code). Instead, `settings.ts: researchFolderWarning()` is a non-blocking sanity check called from both the imperative `onChange` and the declarative `setControlValue()`: if the typed path resolves to an existing file (not a folder) it warns; if it doesn't exist yet it warns but still saves the value, since `view.ts: createAndLinkResearchNote()` creates the folder automatically the first time a note is actually added there. Surfaced via `Notice`, not a persisted inline error — deliberately not wired through the declarative API's `validate` hook, which *rejects* (doesn't persist) a value on a non-empty return, which is wrong here since a not-yet-existing folder is a valid, expected state.
- Toggling the feature off never deletes `researchNotePath` from any record — it only stops rendering the column. Deleting the whole row (`deleteValuation()`) is still what removes a link for good, same as it removes everything else about that ticker. Link/unlink call `persistValuations([ticker])` — the link is a property of that ticker's note.

### Valuation history (implementation)

- Data: `HistoryEntry` (`valuationStore.ts`) — `at` (epoch ms, doubles as dedupe key and chart x-axis), `price`, `dcfBearIv`/`dcfBaseIv`/`dcfBullIv`, `grahamBearIv`/`grahamBaseIv`/`grahamBullIv`, `tenCapIv`, `impliedGrowth`, and optional `ddmBearIv`/`ddmBaseIv`/`ddmBullIv` (absent on entries recorded before the DDM existed). No MoS fields — always derived from `iv`/`price` via `calculations.ts: marginOfSafety` at render time, never stored, so a formula change can't leave stale MoS sitting in old entries. `SavedValuation.history?: HistoryEntry[]`, omitted (not `[]`) once empty, same convention as `researchNotePath`/`lastPriceRefreshAt`. Purely additive to the schema — no `CURRENT_SCHEMA_VERSION` bump, same reasoning as those two optional fields.
- Logic: `historyStore.ts`, Obsidian-free and fully unit tested (`tests/historyStore.test.ts`). `appendHistoryEntry` replaces any existing entry from the same **local** calendar day rather than accumulating one per save; `deleteHistoryEntry` removes by exact timestamp; `compactHistory` collapses anything older than ~182 days to the latest entry per calendar month (local time), leaving recent entries untouched — idempotent, and the caller's job to gate behind a confirmation since it's irreversible.
- Wiring: `historyStore.ts: buildHistoryEntry(at, scenarios)` builds one `HistoryEntry` from a scenario set (all three scenarios' DCF/Graham/DDM IV, Base's price/Ten Cap/impliedGrowth) — the single place that mapping lives, shared by both callers below. `view.ts: saveValuation()` calls it on the record it just built and runs the result through `appendHistoryEntry`, carrying the prior `history` forward from `this.originalTicker` the same way `researchNotePath`/`lastPriceRefreshAt` are. `refreshAllPrices()` calls it too, per ticker, right after recomputing that ticker's price-derived results — a price refresh earns a history point the same as a Save does, since MoS/IV moving with price is exactly what this timeline tracks; Graham/Ten Cap/DDM end up unchanged entry-to-entry from refreshes since they don't depend on price, same as the live results.
- UI: `view.ts: renderHistorySection()`/`renderHistoryTabulator()`, rendered last on the calculator form (`renderForm()`), after the sensitivity grids — skipped entirely for a brand-new, never-saved valuation (`this.originalTicker === null`). A date-range line (oldest → newest entry) sits under the section header. Read live off `plugin.data.getValuation()`, not copied into form state, same as research links. The table itself is a second `Tabulator` instance (`this.historyTabulator`, torn down in `destroyTabulator()` alongside the others) with the same paginated/sortable/responsive-collapse setup as the main table (`StockValuationsView.PAGE_SIZE` rows/page) — `HistoryRow`/`buildHistoryRow()` flatten a `HistoryEntry` into precomputed IV/MoS pairs the same shape as `TableRow`, and `ivMosFormatter` was genericized (`ivMosFormatter<T>`) so both tables' columns share one formatter. Delete and Compact both go through `ConfirmModal`, then a full `this.render()` — same "just re-render the screen" pattern as every other data-mutating action here (delete/link/unlink), rather than patching the Tabulator instance in place. `renderHistoryChart()` plots one "fair value vs. price" line chart per scenario off the same entries (Chart.js `tension: 0.4` on each dataset for a curved rather than segmented line).
- Docs: `docs.ts: VALUATION_HISTORY_DOC`, rendered in `view.ts: renderDocs()` right after `DATA_SOURCES_DOC` — explicitly states history only accrues forward from the next Save or refresh, since there's no way to reconstruct entries for saves/refreshes made before this feature existed.
- Vault storage: a ticker's whole `history` is the body table of its `TICKER.md` note (`notes/valuationNote.ts`), one row per entry, newest first, raw values (no MoS — that's still derived at render time). See **Data persistence** for when notes are written.

### Your position / average entry (implementation)

- Data: `SavedValuation.avgEntry?` (number) and `entryDate?` (local `YYYY-MM-DD` string) — both optional, omitted when there's no position, and shared by all three scenarios (so they're not in `FormState`; `view.ts` holds them as `avgEntry`/`entryDate` strings alongside `moneyScale`). Purely additive to the schema — no `CURRENT_SCHEMA_VERSION` bump. They're note properties in `TICKER.md` (`notes/valuationNote.ts`), parsed leniently: a non-positive/non-numeric `avgEntry` or a malformed `entryDate` is simply dropped. Edited only in the form's "Your position (optional)" section, on any scenario tab; `saveValuation()` writes them from the form (and drops the date when there's no entry).
- Never stored in the history. `historyStore.ts: entryLinePoints(avgEntry, entryDate, times)` builds the chart's flat "Your entry" dataset on every render: the entry date (clamped to the first history point) followed by a point at **every** later history timestamp — not just two endpoints, because the chart's index-mode tooltip only lists a dataset that has a point at the hovered x. Empty when there's no entry or the date is after the newest point. `parseEntryDate` reads the date as local midnight.
- "MoS @ entry": a fourth column in `renderResults()`'s Margin of safety table when an entry is set — just `marginOfSafety(iv, entry)` per method, no new function.
- Deliberately not in the saved-valuations table (an Entry / Price-vs-entry pair of columns was built and removed).

### History chart zoom (implementation)

`renderHistoryChart()` defines one `buildChart(canvas, zoomed)` closure per scenario and uses it twice: the inline chart (`zoomed = false`, legend hidden — the shared static legend above the row covers it) and the one in `ChartZoomModal` (`zoomed = true`, Chart.js's own legend on, whose default click handler toggles datasets). The modal builds its chart in `onOpen` and destroys it in `onClose`; it is not in `this.historyCharts`, so a screen re-render doesn't touch it. The zoom button is a `clickable-icon` in `.sv-chart-col-head`.

### Data persistence (implementation)

**The vault notes are the source of truth (2.0).** Valuations and settings live in Markdown notes in the notes folder (`settings.historyNotesFolder`, default `Stock Valuations`): `TICKER.md` per ticker and `Settings.md`. `data.json` holds only device-local state (`PluginData`: `notesFolder`, `lastSeenVersion`, the four market caches) — losing it costs a refetch, never user data. The note design (tags, `state`, properties winning over paths, parse-from-text on every load, narrow table writes that refuse an unreadable table) is ported from the sibling plugin `../obs-nestegg`; its `notes/frontmatter.ts`, `table/*` and `storage/VaultPort.ts` are copied, with their tests.

- `dataRepository.ts: DataRepository` owns every read/write of persisted state — `main.ts` and `view.ts` go through `plugin.data.*`. Key methods: `load()`, `getValuation()`/`getAllValuations()`/`tickers()` (reads), `saveValuation(ticker, record)` (whole-record upsert — the calculator form's Save), `deleteValuation(ticker)` (trashes the note — left in place it would reload), `persistValuations(changedTickers)` (rewrite the note of each named ticker, and only those, for callers that mutated a record from `getValuation()` in place — name every changed ticker, research-link edits included), `saveSettings()` (`Settings.md`), `setNotesFolder()` (switch folder and reload; moves nothing), `saveLocalState()` (`data.json` only).
- Layout: `notes/` (pure note text ↔ model: `frontmatter.ts`, `kinds.ts` tags/`state`, `paths.ts`, `valuationNote.ts`, `settingsNote.ts`), `table/` (own Markdown table parser/serializer), `storage/` (`VaultPort` interface; `ObsidianVault` is the only file that touches the vault API and isn't unit tested). A ticker note stores each scenario's `FormState` as flat properties (`base_growth1to5: "8"`, strings exactly as typed; the `Record<keyof FormState, true>` in `valuationNote.ts` makes a new `FormState` field a compile error until it's listed) and the history as a table whose `At` column is the exact epoch ms. `Results` are never stored.
- Each ticker's note path is remembered from load (`notePaths`), so a note the user moved or renamed is still written in place. A new ticker's note goes to `TICKER.md`, or `TICKER (valuation).md` if something else is already there — never overwritten. Writes are serialized (`enqueue`) so two quick saves of a new ticker can't both create it. A write failure (including a refused unreadable table) is caught per ticker, logged, and reported through `onNoteError(error, subject)`, without stopping other tickers' writes.
- Startup cost of the legacy import is deliberately nil on a normal start: `load()` checks whether `data.json` still has the legacy `settings`/`valuations` keys (in memory, no vault access); only then does it do one `exists()` on `Settings.md`, the import's completion marker. Once an import finishes, `data.json` is rewritten without the legacy keys, so every later start takes the free path (`tests/dataRepository.test.ts` asserts `existsCalls === 0`). The vault listing reads only the notes folder (top level only when the folder is blank).
- Legacy import (`importLegacy`): pre-2.0 `data.json` (migrated v1→v2 in memory by `migrations.ts` if needed) → one note per ticker not already present → `Settings.md` last → reload from notes → drop the legacy keys. A failure before the marker keeps the legacy keys in `data.json` (`legacyKeep`), runs the session from them, and retries on the next start, skipping tickers that already have a note. Old `TICKER-history.md` files are untagged, so they're ignored and never touched. The retired `valuationsNotePath` still seeds the folder (`folderOfPath`) when `historyNotesFolder` was never set.
- Results are never trusted as read: `load()` rebuilds every scenario's `results` from its `state` (`recomputeAllResults`, in memory only, from a copy of each state so inputs — even `mktCap` — are untouched). History entries are snapshots, not derived; `HistoryIv` (`number | null`) types them honestly (a `NaN` is an empty cell and reads back `null`), and readers go through `historyIv()`. `format.ts` checks `Number.isFinite`, never the global `isFinite`, as a last line of defense.
- Deliberately Obsidian-runtime-free, same reasoning as `historyStore.ts`/`migrations.ts` (the `obsidian` npm package ships type declarations only, no runtime). `PluginDataAdapter` (`loadData`/`saveData`) is satisfied structurally by Obsidian's `Plugin`; the vault is the injected `VaultPort`, faked in tests by `tests/helpers/memoryVault.ts`.
- New `FormState` fields need no migration: `view.ts: loadIntoForm()` lays each saved scenario's state over `blankFormState()`, and a property missing from an older note reads as `""`. Calculations already treat a missing field as 0 (`valuationCalc.ts: numFromState`). (`CURRENT_SCHEMA_VERSION` now only guards the legacy `data.json` import.)
- Covered by `tests/dataRepository.test.ts` (loading from notes, reinstall, moved/duplicate/unreadable/in-transit notes, the import and its failure/retry paths, the startup-cost assertions, CRUD, settings, folder switch, cache TTLs) plus `tests/notes/*` and `tests/table/*`.

## Development

```
make install     # npm install
make dev         # build main.ts and watch for changes (unminified, inline sourcemaps)
make build       # typecheck, then produce a minified production main.js
make typecheck   # tsc -noEmit over the project
make test        # run the test suite once (vitest)
make test-watch  # run tests in watch mode
make clean       # remove build output (main.js, main.js.map)
```

Run `make help` for the full list of targets.

### Testing

`calculations.ts`, `valuationCalc.ts`, `scenarioValidation.ts`, `fundamentalsProvider.ts`, `notes/*`, `table/*`, `format.ts`, `units.ts`, `historyStore.ts`, `migrations.ts`, and `dataRepository.ts` are pure/Obsidian-runtime-free and framework-agnostic, so they're covered by unit tests under `tests/` (Vitest) — `dataRepository.ts` via a fake `PluginDataAdapter` rather than the real Obsidian `Plugin`. The rest of the plugin (`main.ts`, `view.ts`, `settings.ts`, `noteSync.ts`, `priceProvider.ts`) is written directly against the Obsidian API/DOM and isn't currently unit tested — verify changes there by loading the built plugin in a vault (`make build`, then copy `main.js`/`manifest.json`/`styles.css` into `<vault>/.obsidian/plugins/stock-valuations/` and reload Obsidian).

### Build

`esbuild.config.mjs` bundles `main.ts` into `main.js`, marking `obsidian`, `electron`, and the CodeMirror/`@lezer` packages as external (they're provided by the Obsidian runtime). `make dev` runs an esbuild watch context with inline sourcemaps; `make build` typechecks first, then produces a minified, sourcemap-free production bundle.

### Compatibility

`manifest.json` pins `minAppVersion` to `1.7.2`. The declarative settings API (`getSettingDefinitions()`, `toggle`/`folder`/`file` control types, per-item `visible`) is 1.13.0+ only and is ignored on older Obsidian, which falls back to the imperative `display()` in `settings.ts` — when adding a setting, add it to both and keep them behaviorally equivalent. Everything else used (`Menu`, `FuzzySuggestModal`, `normalizePath`, `TFile`, etc.) predates 1.7.2.
